# 构建发布与本地安装

> 最后核对：2026-10-24 ｜ 对应版本：0.6.11

## 一、前置条件

- Node.js **≥ 24**（见 `package.json` 的 `engines`）。
- Windows / macOS / Linux 均可开发；Windows 安装包由 NSIS 生成。
- **用 `npm install`，不要用 `npm ci`**：`package-lock.json` 与 `package.json` 有漂移，`npm ci` 会报 `EUSAGE`。

```bash
npm install
```

## 二、常用命令

| 命令 | 用途 |
|---|---|
| `npm run dev` | 浏览器开发（Vite） |
| `npm run dev:electron` | Electron 开发（需先准备 windowtolayer / wallpaper-helper） |
| `npm run typecheck` | TypeScript 类型检查 |
| `npm run test:unit` | Vitest 单元测试 |
| `npm run test:ui` | Playwright UI 测试（需要 4173 dev server） |
| `npm run test:component` | Playwright 组件测试 |
| `npm run build:electron` | 构建前端 + 原生 helper + NSIS 安装包 |
| `npm run codemap` | 重新生成 `docs/CODEMAP.md` |
| `npm run codemap:check` | 检查代码地图是否过期 |

UI 测试注意：`playwright.config.ts` 会自己拉起 `127.0.0.1:4173` 的 dev server（`reuseExistingServer: true`），5 个 worker，失败重试 1 次。单条用例可用 `npx playwright test test/ui/xxx.spec.ts --project=e2e`。

## 三、开发模式

```bash
# 浏览器
npm run dev

# Electron（首次或原生 helper 变更后）
npm run dev:electron
```

`dev:electron` 需要 `build/windowtolayer` 与 `build/folia-wallpaper-helper.exe`；改原生 helper 时先跑对应构建脚本。

## 四、构建 Windows 安装包

```bash
npm run build:electron
```

它会依次：

1. `vite build`（`ELECTRON=true`，保证产物用相对路径，否则打包后白屏）。
2. `packaging/verify-electron-dist.mjs` 校验产物。
3. 构建 windowtolayer（非 Linux 会跳过）与 wallpaper-helper。
4. electron-builder 生成 `release\win-unpacked` 与 `release\Folia-Setup-<版本>.exe`、`.blockmap`、`latest.yml`。

**已知问题**：打包阶段偶发 `read ECONNRESET`，直接重试一次通常就过（EXP-0006）。仍失败时检查：

- `%LOCALAPPDATA%\electron\Cache` 是否有对应 Electron 版本 zip；
- `%LOCALAPPDATA%\electron-builder\Cache` 是否有 nsis / nsis-resources / 7zip；
- 网络是否需要代理。

## 五、本地安装与启动

1. 关闭正在运行的 Folia：
   ```powershell
   Get-Process Folia -ErrorAction SilentlyContinue | Stop-Process -Force
   ```
2. 静默安装：
   ```powershell
   Start-Process -FilePath "release\Folia-Setup-<版本>.exe" -ArgumentList "/S" -Wait
   ```
3. 启动前清掉 `ELECTRON_RUN_AS_NODE`（否则打包应用会直接退出，EXP-0007）：
   ```powershell
   Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
   Start-Process "$env:LOCALAPPDATA\Programs\Folia\Folia.exe"
   ```
4. 安装目录：`%LOCALAPPDATA%\Programs\Folia`。
5. 验证：窗口标题出现 `Folia`；`resources\app.asar` 时间戳与构建时间一致。

## 六、发布流程（必须先获得用户明确授权）

> 未经用户点头，**不创建 Release、不上传安装包、不改更新通道**。

1. 确认 `git status` 干净、`npm run typecheck` 与相关测试通过。
2. 改 `package.json` / `package-lock.json` 的 `version`，提交 `release: x.y.z`。
3. 构建，实际安装启动验证（至少：启动、播放、暂停歌词、WE、侧栏/效果器）。
4. 记录安装包大小与 SHA-256。
5. 在 `2706521883-lgtm/folia-updates` 创建 Release，上传：
   - `Folia-Setup-<版本>.exe`
   - `.exe.blockmap`
   - `latest.yml`
6. 用 API 核对 `latest.yml` 的版本与哈希；重新下载安装包校验 SHA-256。
7. 更新「传输」文件夹：只留最新本地安装包 + 官方 `Folia_0.7.19_Setup.exe`。
8. 把发布状态写进 `05-当前状态与下一步.md` 和 `09-会话日志.md`。

### 上传网络

- `github.com:443` 可能被封锁；`api.github.com` 通常可用。
- 本机 GitHub 通道：`E:\harmessDS\_gh\github-channel.ps1`（`127.0.0.1:8899`），计划任务 `GitHubChannelWatchdog`。
- 通道没起来时，git 可绕过失效代理并钉 IP：
  ```bash
  git -c http.https://github.com/.proxy= \
      -c http.curloptResolve=github.com:443:<可用IP> push origin <branch>
  ```
- 大文件上传走本地 mihomo 代理 `http://127.0.0.1:9674`，必要时 `curl --http1.1`；分文件上传并校验哈希（EXP-0011）。
- `gh` CLI 未安装；用 GitHub REST API，token 在 `~/.git-credentials`，不要外发。

## 七、版本与产物核对

```powershell
Get-Item "release\Folia-Setup-<版本>.exe" | Select-Object Length, LastWriteTime
(Get-FileHash "release\Folia-Setup-<版本>.exe" -Algorithm SHA256).Hash
```

- 安装包文件名：`Folia-Setup-<版本>.exe`（electron-builder `artifactName`）。
- `latest.yml` 由 electron-builder 生成；发布前确认 `version` 与 `package.json` 一致。
- 「传输」文件夹路径：`C:\Users\ZIMO\Desktop\传输`。

## 八、回滚

- 代码：切回上一个 `release/<版本>` 分支，重新构建。
- 线上：在 `folia-updates` 保留旧 Release；不要删除旧资产，除非用户明确要求。
- 本地：重新安装旧版本安装包；用户数据在 `%APPDATA%\Folia`，降级前先备份。

## 十、收尾同步（本地 → 桌面 → GitHub）

时间戳格式、台账与断档处理的完整规则见 `11-同步与时间戳.md`；本节只列执行步骤。

收尾不是只改本地文件，必须让三处对齐：

| 层级 | 位置 | 角色 |
|---|---|---|
| GitHub | `origin/release/<版本>` 里的 `docs/handbook/` | 已发布真相；换电脑/新会话 clone 后读这里 |
| 本地仓库 | `docs/handbook/` | 编辑副本 |
| 桌面镜像 | `C:\Users\ZIMO\Desktop\Folia-项目手册\` | 快速阅读；新会话可直接扫 |

顺序：

1. 按“删除 + 替换 + 合并”更新手册，并更新 `05` / `07` / `08` / `09`。
2. 同步桌面并校验：
   ```bash
   cp docs/handbook/*.md "C:/Users/ZIMO/Desktop/Folia-项目手册/"
   diff -r docs/handbook "C:/Users/ZIMO/Desktop/Folia-项目手册"
   ```
3. 提交（手册 + 本次代码改动）：
   ```bash
   git add docs/handbook CLAUDE.md README.md <本次代码文件>
   git commit -m "docs(handbook): 收尾更新 YYYY-MM-DD"
   ```
4. 推送并核对：
   ```bash
   git push origin release/<版本>
   git ls-remote origin refs/heads/release/<版本>
   ```
   远端 HEAD 必须等于本地 `git rev-parse HEAD`。
5. 在 `09-会话日志.md` 记录“已推送 `<commit>`”或失败原因。
6. 更新 `05-当前状态与下一步.md` 的时间戳与三副本台账；网盘未备份就写“未记录”。

**推送失败**：保留本地提交；桌面已同步；在 `09` 和 `05` 标“待推送”，下次会话先补推再继续。不要把“本地已改”当成“已同步”。

> 推送手册/代码不是发布版本；创建 Release、上传安装包仍然必须单独获得用户明确授权。

## 十一、改名清单（Runbook）

项目改名时按下面顺序做，**不要直接全局替换**。

### 11.1 先定身份

1. 更新 `01-项目总览.md` 第〇节“项目身份”表。
2. 判断 `appId` / `productName` 是否要改：
   - 只改展示名：风险低，保留 `appId` 与用户数据路径。
   - 连结构标识一起改：必须设计用户数据迁移、升级链和发布说明，否则老用户会变成“新应用”。

### 11.2 代码与构建

| 位置 | 要检查什么 |
|---|---|
| `package.json` | `name`、`productName`、`build.appId`、`build.publish`、`artifactName`、NSIS 文案 |
| `electron/main.cjs` | 发布 URL、窗口标题、托盘、用户数据路径相关逻辑 |
| `electron/updateChannels.cjs` | 更新通道与发布仓库是否仍匹配 |
| `src/i18n/locales/*` | 品牌名、界面文案 |
| `README.md`、`AGENTS.md`、`docs/**` | 标题、链接、示例命令 |
| `test/**` | 断言里的品牌名、快照 |
| 安装目录 / 用户数据目录 | 由 `productName` 决定，改名后旧数据不会自动跟过去 |

### 11.3 外部身份

- GitHub 源码仓库改名 → `git remote set-url origin <新地址>`。
- 发布仓库改名 → `package.json` 的 `build.publish` 与 `FOLIA_RELEASES_URL` 同步。
- `latest.yml` / 安装包里的 `app-update.yml` 会随构建重新生成。
- 桌面手册目录、传输文件夹、快捷方式、记忆文件里的路径同步改名。
- 旧仓库/旧域名尽量保留重定向或至少一条迁移说明。

### 11.4 验证

1. 全新安装 + 从旧版本升级各一次。
2. 检查更新能到达新发布仓库。
3. 检查用户数据（设置、登录态、缓存）是否仍能找到。
4. 旧安装目录/旧快捷方式是否需要清理。
5. `rg` 旧名，确认只剩一处“曾用名/迁移说明”。

### 11.5 更新手册

- 改 `01` 身份表、`02/03` 路径、`04` 本清单、`05` 当前状态、`06` 决策、`09` 日志。
- 旧名只在**一处**保留迁移说明，其余全部替换；不要让旧名散落。

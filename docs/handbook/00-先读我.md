## 四、收尾触发词与固定动作

**收尾是手动触发的阶段性快照，不是实时更新。**

平时正常开发，不逐条改手册；只有用户明确说 **“收尾 / 今天做到这里 / 做到一定程度了 / 更新说明书 / 记录一下”** 时，才做一次完整整理。

收尾的第一步不是改文件，而是**先总结这段时间**：目标是什么、做了哪些改动、验证结果如何、留下了什么结论和下一步。总结清楚后，再按下面的顺序更新：

1. **覆盖** `05-当前状态与下一步.md`：只保留当前真相，删除过期状态。
2. **删** `08-已知问题与坑.md` 里已经修好的条目；值得复用的写进 `07-经验库.md`。
3. **检查** `01/02/03/06` 是否有因今天的改动而失效的旧描述，有就改或删。
4. **追加**一条 `09-会话日志.md`；超过 10 条就把旧的合并成里程碑摘要。
5. 更新所有改动文件顶部的“最后核对时间”：`YYYY-MM-DD HH:mm（UTC+8）`，并更新 `05` 的三副本台账。
6. 检查行数预算；超了就合并、压缩、删旧内容，**不许无脑追加**。
7. **同步桌面镜像**：把仓库 `docs/handbook/` 复制到 `C:\Users\ZIMO\Desktop\Folia-项目手册\`，并 `diff -r` 确认一致。
8. **提交到 git**：`git add docs/handbook CLAUDE.md README.md`（以及本次代码改动），提交信息用 `docs(handbook): 收尾更新 YYYY-MM-DD` 或按实际代码 scope；收尾后工作区应干净，若有未完成改动必须明确记录。
9. **推送到 GitHub**：`git push origin release/<版本>`；网络失败时按 `04-构建发布与本地安装.md` 的绕行处理；推送后用 `git ls-remote` 核对远端 HEAD 与本地一致。
10. **记录同步结果**：在 `09-会话日志.md` 写“已推送 `<commit>`”或“推送失败：原因；本地已提交、桌面已同步，下次重试”。

> 推送手册和推送代码不是“发布版本”：Release 仍然必须单独获得用户明确授权。

### 4.1 时间戳与台账

所有状态记录用 **`YYYY-MM-DD HH:mm（UTC+8）`**；每次收尾更新 `05` 的三副本台账。换电脑或网盘断档时，按 [`11-同步与时间戳.md`](11-同步与时间戳.md) 对比时间，再决定 pull / merge / 覆盖；禁止用旧副本覆盖新副本。

## 五、维护规则（这套手册的核心纪律）

1. **更新 = 删除 + 替换 + 合并，不是追加。**
2. 状态类内容只保留“当前真相”；历史只在 `09-会话日志.md` 里，且有上限。
3. 问题修好就从 `08` 删除；可复用的根因/解法写进 `07`。
4. 同一根因的多个经验合并成一条；架构变了、问题不可能再出现的经验删除。
5. 新功能完成的定义包含“手册同步更新”，不是等收尾才补。
6. 结构保持稳定；只有内容确实装不下时才拆新文件，拆之前先合并旧内容。
7. 不重复：README、CODEMAP、专项文档已有的内容只放链接，不整段抄。
8. **三处副本的层级**：GitHub 仓库里的 `docs/handbook/` 是已发布真相；本地仓库是编辑副本；桌面文件夹是快速阅读镜像。收尾必须让三处对齐。
9. **推送失败不算收尾完成**：本地提交 + 桌面同步只是“待推送”，要在日志和下一次接手时明确标出，网络恢复后补推。
10. **名字是变量**：项目身份表在 `01-项目总览.md` 第〇节；改名按 `04-构建发布与本地安装.md` 第十一节执行。先分类（展示名 / 结构标识 / 外部身份），禁止全局盲替换 `appId`、`productName`、仓库和更新源。
11. **时间戳是同步锚点**：所有状态记录精确到 `YYYY-MM-DD HH:mm（UTC+8）`；每次收尾更新 `05` 台账；断档处理见 `11-同步与时间戳.md`。
